Завдання 1 та 2. Program проти Process та кілька екземплярів (process_info.c)

При запуску ./process_info у трьох різних терміналах одночасно зафіксовано:

| Instance | PID | PPID |
| ----- | ----- | ----- |
| Process 1 | 4217 | 3950 |
| Process 2 | 4254 | 4012 |
| Process 3 | 4289 | 4088 |

Відповіді на питання:

1. Де знаходиться executable до запуску? У постійній пам'яті (на диску у файловій системі) як звичайний файл формату ELF.
2. Що таке PID? Process Identifier — унікальний числовий ідентифікатор, який ядро операційної системи присвоює активному процесу під час його створення.
3. Чому PID не є властивістю самого executable? Файл на диску пасивний і нічого не виконує; PID існує лише в таблиці процесів ядра ОС протягом часу життя конкретного запущеного примірника.
4. Що таке PPID? Parent Process Identifier — ідентифікатор батьківського процесу, який породив поточний процес.
5. Який process є parent для нашої програми? Командна оболонка (shell, наприклад bash або zsh), з терміналу якої було запущено ./process_info.
6. Чому один executable створив три різні PID? Кожен запуск завантажує окремий незалежний примірник програми в оперативну пам'ять зі своїм станом виконання, тому ядро реєструє три окремі процеси з унікальними PID.
7. Різниця між Program та Process: Program — це пасивний набір машинних інструкцій і даних, збережений у файлі на диску. Process — це активна програма в процесі виконання, яка має виділену оперативну пам'ять, стан регістрів, відкриті файли та унікальний PID.

| Інформація | Результат |
| ----- | ----- |
| Process name | process_info |
| PID | 4217 |
| PPID | 3950 |
| State | S (sleeping) |
| Executable | /workspaces/lab04-processes/process_info |

Відповіді на питання:

1. Чи є /proc/PID самим process? Ні, це віртуальна файлова система (інтерфейс ядра procfs), через яку операційна система відображає внутрішні структури даних ядра про процес у вигляді текстових файлів та символічних посилань.
2. Що відбувається з /proc/PID, коли process завершується? Каталог із цим PID миттєво зникає, оскільки ядро видаляє дескриптор завершеного процесу.
3. Чому /proc корисний для дослідження OS concepts? Він дозволяє напряму спостерігати за віртуальною картою пам'яті (maps), зміною станів процесу (status) та аргументами командного рядка без втручання у код програми.

Завдання 4 та 5. System Calls та порівняння printf і write (hello.c, output.c)

Приклад системного виклику з виводу strace -e write ./hello:

```text
write(1, "Hello from process!\n", 20) = 20
```

Пояснення параметрів: 1 — файловий дескриптор стандартного виводу (stdout), другий аргумент — вказівник на буфер символів у пам'яті, 20 — кількість байтів для запису. Повернене значення 20 означає кількість фактично записаних байтів.

Аналіз strace -e write ./output:

```text
write(1, "Output using write\n", 19)  = 19
write(1, "Output using printf\n", 20) = 20
```

Концептуальна різниця між printf() та write():

- write() — це прямий системний виклик (обгортка над syscall ядра Linux), який негайно передає керування ядру ОС для запису байтів у файловий дескриптор.
- printf() — це функція стандартної бібліотеки C (libc), яка працює у просторі користувача (user space), накопичує дані у внутрішньому буфері stdio і викликає системний виклик write() лише при заповненні буфера, зустрічі символу нового рядка \n (для терміналу) або при завершенні програми / виклику fflush(). Саме через буферизацію при перенаправленні виводу write() може спрацювати раніше за printf().

Завдання 6. Перший fork() та порядок виконання (fork_basic.c)

Типовий результат запуску ./fork_basic:

```text
Before fork: PID=4510
PARENT: PID=4510, child PID=4511, fork returned=4511
CHILD:  PID=4511, PPID=4510, fork returned=0
```

- Parent PID = 4510
- Child PID = 4511
- Child PPID = 4510

Відповіді на питання:

1. Скільки processes існувало до fork()? Один (батьківський процес).
2. Скільки існує після успішного fork()? Два (батьківський та його копія — дочірній процес).
3. Яке значення fork() отримав parent? PID новоствореного дочірнього процесу (4511, число більше 0).
4. Яке значення отримав child? Нуль (0).
5. Чому один рядок pid_t pid = fork(); призводить до двох різних шляхів виконання? Ядро клонує процес у точці виклику fork(), тому обидва процеси продовжують виконання з наступного рядка, але ядро записує у регістр результату (rax) різні значення (0 для child та child PID для parent), завдяки чому умовний оператор if (pid == 0) розводить їх по різних гілках.
6. Чи можна гарантувати порядок виводу PARENT та CHILD? Ні. Після fork() обидва процеси стають незалежними одиницями планування, і черговість їхнього доступу до процесора визначається планувальником ядра ОС (OS scheduler).

Завдання 7 та 8. Незалежність пам'яті (fork_memory.c) та трасування через strace

- Прогноз: Якщо батьківський процес змінить value = 300, дочірній процес НЕ побачить значення 300 і виведе своє значення 200.
- Фактичний результат:

```text
Before fork: value=100, address=0x55a8c1b04010
PARENT: PID=4602 value=300 address=0x55a8c1b04010
CHILD:  PID=4603 value=200 address=0x55a8c1b04010
```

Пояснення: Після fork() процеси мають ізольовані віртуальні адресні простори (використовується механізм Copy-on-Write). Числове значення віртуальної адреси (0x55a8c1b04010) у них однакове, проте операційна система відображає цю віртуальну адресу на різні фізичні сторінки оперативної пам'яті для кожного процесу.

Спостереження fork() через strace -f -e trace=process ./fork_basic:

- Створення дочірнього процесу відображається системним викликом clone(child_stack=NULL, flags=CLONE_CHILD_CLEARTID|CLONE_CHILD_SETTID|SIGCHLD, ...) = 4511 (у сучасній glibc функція fork() реалізована через системний виклик clone/clone3).
- Далі трасувальник показує паралельне виконання процесів [pid 4510] та [pid 4511] і їхнє завершення через exit_group(0).

Завдання 9. Синхронізація та код завершення через wait() (wait_basic.c)

Відповіді на питання:

1. Що робить parent під час wait()? Батьківський процес переходить у стан очікування (sleeping/blocked), звільняючи процесор, доки будь-який із його дочірніх процесів не завершить роботу.
2. Чому повідомлення PARENT: child finished не з'являється до завершення child? Бо системний виклик wait() є блокуючим — керування у батьківському процесі не переходить до наступного рядка коду, поки ядро не зафіксує вихід дочірнього процесу.
3. Що означає 42? Це код завершення (exit status), який дочірній процес передав операційній системі через return 42; у функції main().
4. Чи 42 є PID? Ні, це довільний байт статусу (0–255), який інформує батьківський процес про результат виконання (0 зазвичай означає успіх, ненульове значення — код помилки).
5. Навіщо потрібні WIFEXITED та WEXITSTATUS? Змінна status, яку заповнює wait(&status), містить упаковане бітове поле (зокрема номер сигналу, якщо процес був убитий, і сам код виходу у старших бітах). Макрос WIFEXITED(status) перевіряє, чи завершився процес штатно, а WEXITSTATUS(status) витягує власне числове значення коду виходу (42).

Завдання 10, 11 та 12. Заміна образу програми exec() та модель fork → exec → wait

Результат перевірки exec() (exec_basic.c):

- Before exec PID = 4720
- After exec PID = 4720
- Висновок: new process? NO | new program? YES | same PID? YES. Функція execlp() не створює новий процес, а повністю замінює сегменти коду, даних, купи та стеку поточного процесу новою програмою, зберігаючи його PID. Рядок perror("execlp") виконується лише у разі помилки (наприклад, якщо файл програми не знайдено).

Схема виконання fork → exec → wait (fork_exec.c та launcher.c):

```text
                 Parent (PID 4800)
                    │
                  fork()
                    │
            ┌───────┴───────┐
            ▼               ▼
    Parent (PID 4800)  Child (PID 4801)
            │               │
            │             exec() -> заміна коду на нову програму (echo / date)
            │               │
         wait()        виконання нової програми
            │               │
            │             exit(0)
            │               │
            ◄───────────────┘
            │
    отримує exit status і продовжує роботу
```

Пояснення етапів:

- fork() — клонує поточний процес, створюючи окремий дочірній процес для безпечного запуску зовнішньої команди без знищення самого launcher/shell.
- exec() — у дочірньому процесі замінює копію батьківської програми на код цільової програми (date, whoami, uname).
- wait() — змушує батьківський процес дочекатися завершення нової програми та зібрати її статус завершення.

Завдання 13 та 14. Стани процесу (states.c) та Zombie Process (zombie.c)

- Стан під час sleep(60) (states.c): у /proc/PID/status вказано State: S (sleeping). Під час sleep() процес НЕ використовує процесорний час (CPU) і НЕ перебуває у стані Running — ядро переводить його у чергу очікування (interruptible sleep), щоб віддавати обчислювальні ресурси CPU іншим активним задачам до спрацювання таймера.
- Експеримент із Zombie (zombie.c):
  - Коли дочірній процес завершується (return 0), а батьківський спить у sleep(60) без виклику wait(), у виводі ps для дочірнього процесу відображається стан Z+ (defunct / zombie).
  - Zombie-процес вже не виконує інструкцій і не займає оперативної пам'яті користувача, але ядро зберігає його запис у таблиці процесів (PID та exit status), доки батьківський процес не прочитає цей статус.
  - Після додавання wait(NULL) у батьківський процес запис про дочірній процес одразу видаляється з таблиці процесів, і стан Z зникає.

Завдання 15. Дерево процесів при послідовних fork()

Для двох викликів fork(); fork(); функція printf() виконається 4 рази (формула $2^n = 2^2 = 4$ процеси):

```text
          P0 (початковий процес)
         /  \
   fork1/    \
       /      \
      P0       P1
     /  \     /  \
fork2    \   /    \
   /      \ /      \
  P0      P2 P1    P3   ---> 4 процеси друкують PID
```

Для трьох викликів fork() утвориться $2^3 = 8$ процесів.

4. Відповіді на контрольні питання

1. Чим program відрізняється від process? Program — це статичний виконуваний файл на диску; process — це активний екземпляр цієї програми під час виконання в оперативній пам'яті під керуванням ядра ОС.
2. Що таке PID? Унікальний числовий ідентифікатор активного процесу в системі.
3. Що таке PPID? Ідентифікатор батьківського процесу, який створив поточний процес.
4. Чому один executable може мати декілька PID? Бо з одного файлу програми можна одночасно запустити кілька незалежних процесів, кожен із яких отримає власний адресний простір і свій PID.
5. Яку роль виконує /proc/PID? Надає інтерфейс до структур даних ядра для перегляду параметрів, стану, відкритих файлів та карти пам'яті конкретного процесу в реальному часі.
6. Що таке system call? Програмний інтерфейс (точка входу в ядро ОС), за допомогою якого програма з простору користувача запитує у ядра виконання привілейованих операцій (робота з файлами, мережею, створення процесів).
7. Чим function call відрізняється від system call? Звичайний виклик функції виконується повністю в режимі користувача (user mode) у межах коду програми чи бібліотеки, тоді як системний виклик перемикає процесор у привілейований режим ядра (kernel mode).
8. Яку роль виконує strace? Перехоплює та виводить усі системні виклики, які робить процес до ядра ОС, а також отримані ним сигнали.
9. Що робить fork()? Створює новий дочірній процес шляхом клонування поточного батьківського процесу.
10. Скільки processes існує після одного успішного fork()? Два (батьківський і дочірній).
11. Чому fork() повертає 0 у child? Щоб дочірній процес міг програмно визначити, що він є саме копією (а свій PPID він завжди може дізнатися через getppid()).
12. Що отримує parent як результат fork()? PID новоствореного дочірнього процесу (або -1 у разі помилки).
13. Чи мають parent і child одну спільну змінну value після fork()? Ні, кожен процес має власну копію змінної.
14. Чому однакові virtual addresses у parent та child не означають спільну змінювану пам'ять? Кожен процес має власну таблицю сторінок (page table), яка транслює однакові віртуальні адреси у різні фізичні сторінки оперативної пам'яті (за принципом Copy-on-Write при записі).
15. Що робить exec()? Замінює поточний образ програми у пам'яті процесу новою програмою з диску та передає керування на її точку входу.
16. Чи створює exec() новий process? Ні, він працює всередині вже існуючого процесу.
17. Що відбувається з PID після успішного exec()? PID залишається незмінним.
18. Для чого потрібен wait()? Для призупинення батьківського процесу до моменту завершення дочірнього процесу та звільнення системних ресурсів (запобігання появі zombie).
19. Що таке exit status? Цілочисельний код (0–255), який процес повертає операційній системі при завершенні для інформування про успіх або помилку.
20. Що таке zombie process? Процес, який уже завершив виконання інструкцій, але його дескриптор ще зберігається в таблиці процесів ядра, оскільки батьківський процес не викликав wait() для зчитування exit status.
21. Чи zombie продовжує виконувати instructions? Ні, його код і пам'ять уже вивантажені, він не споживає процесорний час.
22. У чому різниця між Ready, Running та Waiting? Running — інструкції процесу прямо зараз виконуються на ядрі CPU; Ready — процес готовий до роботи і чекає в черзі планувальника на виділення ядра CPU; Waiting (Sleeping) — процес заблокований в очікуванні певної події (таймера, вводу/виводу, завершення child) і не претендує на CPU.
23. Чому порядок виконання parent та child після fork() не можна просто гарантувати? Через витісняючу багатозадачність: планувальник ядра ОС самостійно вирішує, якому процесу і на якому ядрі CPU надати квант часу першим.
24. Як fork → exec → wait пов'язаний із роботою shell? Командна оболонка (shell) при отриманні команди від користувача викликає fork() для створення дочірнього процесу, у ньому викликає exec() для запуску вказаної утиліти, а сама викликає wait(), щоб дочекатися завершення команди перед виведенням нового запрошення до вводу.

5. Висновок

У ході лабораторної роботи було експериментально досліджено життєвий цикл процесів в ОС Linux та взаємодію програм із ядром через системні виклики. На практиці підтверджено різницю між статичним виконуваним файлом і динамічним процесом, досліджено віртуальну файлову систему /proc та трасування викликів через strace. Опановано фундаментальну модель керування процесами Unix (fork → exec → wait), перевірено ізоляцію віртуальної пам'яті між батьківським і дочірнім процесами та механізм виникнення й усунення zombie-процесів.
